# APMS v2 — API Contract

Base path: `/api/v1`. All responses JSON. All timestamps RFC 3339 with offset.

Getting this boundary right on Day 8 is what makes Days 9–15 go fast. Lock it
before writing the worker.

---

## Authentication

**Workers** send a device token:
```
Authorization: Bearer apms_dev_<40-char-random>
```
Issued once when a camera is created, shown once, stored hashed. Scoped to a
single camera. If leaked, rotate the camera's token — blast radius is one camera.

**Humans** use session auth for the dashboard.

Never accept a device token on a human endpoint or vice versa.

## Worker endpoints

### `GET /worker/config`

Called on startup and every 5 minutes. The worker holds no persistent config of
its own.

**200:**
```json
{
  "camera_id": "3f2a...",
  "lot_name": "Labim Mall",
  "source_uri": "file:///data/demo.mp4",
  "reference_frame": { "width": 1280, "height": 720 },
  "model": {
    "version": "mnv3s-pklot-20260901",
    "url": "https://.../mnv3s-pklot-20260901.onnx",
    "sha256": "9c1f...",
    "input_size": [96, 96]
  },
  "smoothing": { "window": 9, "min_agreement": 6 },
  "sampling": { "target_fps": 2 },
  "slots": [
    {
      "id": "a91c...",
      "label": "A-01",
      "polygon": [[120,340],[186,338],[190,382],[124,384]]
    }
  ],
  "config_version": 14
}
```

`config_version` increments on any change. The worker compares it and only
rebuilds its slot map when it differs.

`target_fps` of 2 is deliberate. Occupancy changes over minutes; processing at
15fps burns CPU for nothing. This is a defensible engineering decision — mention
it in the writeup.

The model is fetched once and cached by sha256. Do not re-download every restart.

### `POST /worker/events`

Batched state changes. **Only send on transition**, never per frame.

**Request:**
```json
{
  "camera_id": "3f2a...",
  "events": [
    {
      "id": "6b1e-...",
      "slot_id": "a91c...",
      "previous_status": "VACANT",
      "status": "OCCUPIED",
      "confidence": 0.94,
      "observed_at": "2026-09-01T10:22:31+05:45",
      "model_version": "mnv3s-pklot-20260901"
    }
  ]
}
```

**200:**
```json
{ "accepted": 1, "duplicates": 0, "rejected": [] }
```

The `id` is a UUID4 generated by the worker. The server inserts with
`ON CONFLICT (id) DO NOTHING`. This makes retries safe — a timeout followed by a
resend cannot double-count.

Batch limit 500 events. Reject with 413 above that.

Server-side on accept: insert the event, update `SlotState`, publish to
`redis: lot:{lot_id}:updates`.

---

### `POST /worker/heartbeat`

Every 30 seconds.

**Request:**
```json
{
  "camera_id": "3f2a...",
  "fps": 1.94,
  "frames_processed": 3480,
  "queue_depth": 0,
  "model_version": "mnv3s-pklot-20260901",
  "uptime_seconds": 1740
}
```

**200:** `{ "ok": true, "config_version": 14 }`

If `config_version` differs from what the worker holds, it refetches config. This
saves a poll.

Server marks a camera stale after 3 missed heartbeats and sets its slots to
`UNKNOWN`. This is the fix for v1 showing stale vacancy from a dead camera.

## Read endpoints (dashboard)

### `GET /lots`
List lots in the caller's org, each with `total_slots`, `vacant`, `occupied`,
`unknown`, `last_updated`.

### `GET /lots/{lot_id}/slots`
Current state of every slot, with polygon and reference-frame dimensions so the
browser can scale correctly. One scaling path, defined here, used everywhere.

### `GET /lots/{lot_id}/stream` — SSE

```
Content-Type: text/event-stream

event: slot_update
data: {"slot_id":"a91c...","status":"OCCUPIED","confidence":0.94,"at":"..."}

event: heartbeat
data: {"at":"..."}
```

Send a heartbeat comment every 20s to keep proxies from closing the connection.
Backed by the Redis channel the ingest endpoint publishes to.

### `GET /lots/{lot_id}/analytics`
Query params: `from`, `to`, `bucket` (`hour` | `day`).

```json
{
  "occupancy_rate": [{ "bucket": "2026-09-01T10:00:00+05:45", "rate": 0.72 }],
  "dwell_minutes": { "p50": 41, "p90": 137, "mean": 58 },
  "turnover_per_slot_per_day": 3.4
}
```

## Slot management (annotation tool)

### `POST /cameras/{camera_id}/slots:bulk`
Replaces the slot set for a camera in one transaction.

```json
{
  "reference_frame": { "width": 1280, "height": 720 },
  "slots": [
    { "label": "A-01", "polygon": [[120,340],[186,338],[190,382],[124,384]], "slot_type": "STANDARD" }
  ]
}
```

Soft-deactivate slots not present rather than hard-deleting them. v1 ran
`DELETE FROM home_parkingslot` on every restart, orphaning all history. Setting
`is_active = false` preserves the event trail.

## Errors

Uniform shape:
```json
{ "error": { "code": "slot_not_found", "message": "...", "detail": {} } }
```

| Code | Meaning |
|---|---|
| 401 | missing or invalid token |
| 403 | token valid but wrong org or wrong camera |
| 404 | not found, or exists in another org (do not leak existence) |
| 409 | config version conflict on bulk slot write |
| 413 | batch too large |
| 422 | schema validation failed |
| 429 | rate limited |

Return 404, not 403, for cross-org access. A 403 confirms the resource exists.

## Rate limits

| Endpoint | Limit |
|---|---|
| `POST /worker/events` | 60/min per camera |
| `POST /worker/heartbeat` | 4/min per camera |
| `GET /worker/config` | 20/min per camera |
| SSE connections | 5 concurrent per user |

## Contract tests to write in Phase 2

Minimum set. These four catch the v1 bug classes:

1. Org A cannot read org B's lots, slots, or events (expect 404)
2. Posting the same event `id` twice results in one row
3. A device token for camera X cannot post events for camera Y
4. A camera with no heartbeat for 90s has its slots set to `UNKNOWN`
